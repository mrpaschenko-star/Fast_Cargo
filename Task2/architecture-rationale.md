# Техническое обоснование для защиты

Это приложение к [трёхстраничному плану](../Task1/transformation-plan.md). Дальнейшие параметры — проектные предложения, если явно не названы требованиями кейса. [Источники](../sources/README.md).

## 1. Почему постепенная декомпозиция

Задача задаёт демонтаж монолита за год, но запрещает менять его исходники первые три месяца. Поэтому M1–M3 — отдельный аналитический контур, M4–M12 — Strangler Fig с заменой маршрутов по доменам/когортам. Сначала устраняются наиболее опасные границы Payments/Profile, затем отдельный IoT и цепочка заказ–склад–доставка–финансы. Подготовка модульных границ после M3 полезна как шаг миграции, но модульный монолит не является конечной целью задания.

Big Bang потребует одновременно заменить все бизнес-инварианты и не даёт безопасной приёмки частями. Сохранение общей БД оставляет конкуренцию нагрузки и связность. Избыточно дробить каждый CRUD также не нужно: минимум независимых бизнес-контекстов, единая платформа и отдельные владельцы. Event-driven не означает Event Sourcing: источники истины — доменные БД и ledger, события нужны для интеграций и проекций.

## 2. Границы владения и данные

| Контекст | Владелец состояния / хранилище | Контракт и ограничение |
|---|---|---|
| Orders | PostgreSQL: заказ, позиции, workflow/Saga, outbox/inbox | Принимает заказ устойчиво в `pending`; склад/биллинг не вызываются синхронно для принятия заявки |
| Warehouse | PostgreSQL: остаток, резерв, fulfilment, разрешение оплаты | Атомарная проверка остатка в локальной транзакции; единственный владелец stock |
| Delivery | PostgreSQL: рейс, маршрут, назначение, доказательство доставки | Координаты получает как проекцию/ссылку, не сохраняет весь IoT-поток в OLTP |
| Finance | PostgreSQL: invoice, ledger, корректировки, outbox/inbox | Счёт по согласованному milestone; уникальный ключ проводки, неизменяемый аудит |
| Payments | Отдельный PostgreSQL и сегмент: intent, provider_ref, inbox, reconciliation | Нет PAN/CVV; результат только от банка/проверенного webhook; отдельные deployment/доступы |
| Profile | Физически отдельный PostgreSQL, ключи и сеть | Единственный источник ПДн; минимальные scoped API и аудит |
| EDI adapter | Собственный PostgreSQL: документы/receipts и dedup | Маппинг формата партнёра в доменный контракт, не владелец заказов/остатков |
| Telemetry | Отдельная Kafka, ClickHouse и защищённый объектный архив | Append, event-time, device sequence; GPS также чувствительные данные, не экспортируется автоматически |
| History/CRM API | Собственная PostgreSQL read-модель истории | CQRS-проекция из доменных событий; Profile API для разрешённых атрибутов; версия и freshness |
| Analytics export | Приватная проекция + state store преобразования | Проверка полноты, обезличивание, версионная передача во внешний DWH |

«Database-per-Service» означает отдельную БД, роли и запрет чужих SQL; Payments/Profile дополнительно отделяются физически. Для остальных доменов допустима общая управляемая платформа с изолированными кластерами/квотами, но не общий schema ownership. Междоменные ссылки — ID, никаких FK и JOIN через БД. Справочники тарифов/адресов/геозон имеют назначенного мастера холдинга; сервисы используют локальные версионируемые копии. Финансовые/персональные данные не включаются во все события «для удобства».

## 3. CDC к M3 без скрытого SELECT на primary

**Предпосылки.** Физическая standby той же major-версии PG ≥16, проверенные backup/WAL, `wal_level=logical`, физический slot, настройки feedback и доступный запас диска. Конкретные версии PostgreSQL, Debezium/драйвера и режим snapshot фиксируются на стенде. SQL для создания publication/прав и настройка репликации — согласованные DBA-изменения, не правка легаси. Изменение `wal_level` может потребовать рестарт; его нельзя объявить бесплатным для доступности. Для PG ≤15 этот вариант логического чтения standby не подходит: совместимое обновление является отдельной предпосылкой с оценкой риска и срока.

**Изоляция.** Standby разворачивается из уже имеющейся физической копии и WAL, не SELECT-дампа primary. CDC endpoint указывает только на standby. Автосоздание publication и heartbeat SQL, требующий записи, отключаются; publication создаёт DBA. Запрещены служебный polling primary, автоматический fallback endpoint и принудительный `pg_log_standby_snapshot` SELECT на primary. Прогресс оценивается на реплике/по уже доступной телеметрии и журналам, без добавления мониторинговых SELECT на primary.

**Bootstrap — обязательная отдельная проверка.** Стандартный initial snapshot может брать блокировки, недоступные на read-only standby. Нельзя просто включить его и считать задачу решённой. На выбранной связке доказываем согласованный read-only snapshot и границу WAL без блокирующих операций. Если это не поддержано, используем проверенный snapshot-adapter: сначала старт декодирования и буфер WAL, затем консистентный снимок standby, затем упорядоченный replay перекрывающегося интервала до barrier; промежуточные регрессии не публикуются. Все изменения `INSERT/UPDATE/DELETE` и транзакции сверяются до открытия DWH. Это дополнительная работа data-команды; если механизм не прошёл испытание M1, GO запрещён. `snapshot=never` без начального состояния не обеспечивает историю и неизменившиеся заказы.

**Доставка.** Raw-изменения идут в приватную Kafka; адаптер связывает строки в согласованное состояние заказа по transaction metadata, LSN и версии. Схема легаси не считается доменным API. DDL/новые поля проходят совместимость; неизвестная схема останавливает соответствующий экспорт и даёт alarm, не молчаливый пропуск. В промежуточном состоянии bootstrap не выдаётся за SLA realtime. После watermark начальной синхронизации меряем каждый принятый ключевой статус от commit источника до доступности запросу DWH. Последовательные переходы статуса сохраняются как факты, а не только последнее значение.

**Повторы и восстановление.** Ключ CDC включает source/epoch, transaction, LSN и позицию изменения внутри транзакции; один LSN не всегда равен одному событию. Состояние sink и checkpoint обновляются атомарно либо через replay-safe upsert/inbox; commit consumer offset только после durable effect. После падения возможны повторы. На потерю/инвалидацию slot — остановка экспорта, gap marker, восстановление/повторный bootstrap с реплики. Новый epoch не должен обнулить дедупликацию исторических бизнес-фактов. Нельзя обещать автоматический failover всех слотов только потому, что БД реплицируется.

**Задержка.** Предложенный бюджет 1 + 0.5 + 1 + 1.5 + 1 = 5 с. Отдельно наблюдаются репликация, возраст очереди, преобразование, sink visibility и clock skew. Sink в DWH обязан поддерживать непрерывный ingest; минутный batch несовместим с требованием. При сбое DWH задержка может превысить 5 с: это нарушение, фиксируемое SLI, даже когда поток сохранён. Кейс не определяет исключения SLA; их нельзя придумать для успешного отчёта.

## 4. EDI, Saga и невозможность оплаты без обеспечения

EDI использует формат и транспорт партнёра (например, EDIFACT через AS2/HTTPS по договору), внешний TLS/подпись и версионные схемы. Внутри — JSON Schema/Protobuf события в business Kafka, ключ `order_id`, inbox/outbox в каждой доменной БД. Envelope: `event_id`, `type`, `schema_version`, `aggregate_id`, `aggregate_version`, `occurred_at`, `correlation_id`, `causation_id`; PII в payload исключены. Дубликат EDI определяется `(partner_id, document_type, document_id, revision)`; исправление — новая revision, а не повторная операция.

1. **ORDERS.** Adapter устойчиво записывает документ и публикует команду. Orders принимает заявку и запускает Saga. Transport ACK означает доставку документа, а не наличие товара. Warehouse резервирует конкретные позиции локально; при отказе/нехватке Order остаётся pending/rejected с объяснением. Повторы имеют тот же ключ.
2. **DESADV.** Warehouse фиксирует подтверждённую отгрузку с `fulfilment_id`, позициями и версией. Outbox публикует факт; EDI отправляет DESADV и получает receipt. При переупорядочивании документы ждут нужного предшественника, не теряются в DLQ. Статусы внутренних операций и подтверждение партнёра различаются.
3. **INVOIC.** Finance идемпотентно создаёт счёт на разрешённый объём fulfilment. Saga ждёт обязательные milestone/receipts по партнёрскому договору. Выставление счёта не означает подтверждение оплаты. Для частичных отгрузок каждый fulfilment имеет отдельную область сумм/позиций; общая сумма не может превысить согласованный объём.

**Промежуточный M4–M6.** Payments извлекается раньше Warehouse/Finance. После запрета M1–M3 разрешены изменения легаси: тонкие доменные адаптеры и outbox внутри монолита выдают разрешения по тем же локальным инвариантам. Payments не читает общую БД. Только после проверки этого контракта переключаются платежи; в M6–M12 авторитет адаптеров по когортам передаётся новым Warehouse/Finance. Аналогично Profile API замещает legacy-чтение ПДн до их удаления из общей БД.

**Платёжный инвариант.** Проверки «в кешированном остатке >0» недостаточно. Warehouse локально переводит обеспеченный резерв в `payment_authorized`, выпускает одноразовое разрешение, связанное с `payment_intent_id`, суммой, валютой, позициями и версией fulfilment; Finance подтверждает действующий invoice. Для уже отгруженного товара основание — неизменяемое подтверждение отгрузки, а не свободный остаток на полке. Payments создаёт/исполняет платёж только при согласованных разрешениях. Для предоплаты используется отдельный сценарий резерва до отгрузки, а цепочка EDI сохраняет свои milestone.

Finance также закрепляет разрешённую сумму за intent локальной транзакцией: нельзя выпустить второе разрешение на ту же сумму счёта или отменить счёт, пока intent не закрыт. Инвариант защищается уникальным ключом и остатком разрешённой суммы, а не лишь уникальностью UUID.

Пока результат в банке неизвестен, разрешение нельзя отозвать и вернуть товар в свободный остаток по одному TTL. Отмена оформляется через Payments: сначала terminal cancel/expire у провайдера с защитой от позднего исполнения, затем подтверждение Warehouse. Если банк не умеет окончательно отменять открытый intent, резерв удерживается до сверки и ручного разрешения исключения. После оплаченного/отгруженного состояния нужны возврат/credit note/refund, а не откат исторического факта. Так обеспечивается безопасность ценой задержки завершения при разделении сети; мгновенное завершение при недоступном складе не обещается.

Повторы используют exponential backoff с jitter и ограничением общей длительности/числа попыток; DLQ имеет ответственного, alarm и повтор с исходным ключом. Для bank create/capture новый ключ при timeout запрещён. Circuit breaker прекращает новые попытки к упавшей зависимости, но сохраняет pending-команды. Автоматически повторять неидемпотентный API банка нельзя. Численные deadlines и EDI SLA фиксируются с партнёром, не подменяются временем физической доставки.

## 5. Платёжный контур и доступ к профилю

Предпочтение — redirect на домен банка; PAN/CVV не проходят через BFF, gateway, backend, логи или шину Fast Cargo. На сайте используются идентификатор сессии и статус оплаты; фронтенд не читает поля карты. Если понадобится виджет, все элементы сбора карточных данных принадлежат провайдеру и его проверенному origin. CDN, CSP и защита redirect-страницы остаются частью контроля безопасности.

Payments имеет собственный вход webhook, сеть, БД и секреты. Проверка подписи и анти-replay → минимальный allowlisted payload → durable inbox → ACK. Провайдер обязан присылать callback без PAN; body logging отключено. `200` не возвращается до durable записи. При недоступности приёмника используются повторная доставка банка и reconciliation API/реестр за период; redirect в браузере не служит подтверждением. Несколько уведомлений, status polling и поздний callback сходятся в один конечный результат с уникальными ключами и монотонной state machine. Провайдер, не поддерживающий безопасный idempotency/status/reconciliation контракт, не подходит.

«0% потери ответов» трактуется как отсутствие безвозвратно потерянных исходов: сетевые timeout возможны, исход восстанавливается. Нельзя признать потерю устранённой, просто бесконечно оставляя intent pending: ведём возраст/число незавершённых и регламент эскалации. Предел гарантии — доступность и полнота истории банка плюс срок её хранения; эти условия должны быть в договоре.

Profile DB физически изолирована; доступ по краткоживущим credentials, мTLS, RBAC/ABAC и purpose. History API выдаёт статус/маршрут и время обновления из своей проекции; объединение с профилем выполняется авторизованным API, не SQL JOIN. Профиль и GPS остаются в защищённом контуре. Внешние аналитические данные проходят allowlist, исключение свободного текста, точных маршрутов и связующих идентификаторов, обобщение признаков и оценку переидентификации. Окончательный метод обезличивания утверждается ИБ; без этого выгрузка закрыта.

## 6. IoT: устойчивость, ёмкость и backpressure

Устройства → MQTT/HTTPS ingest → отдельная Kafka telemetry → consumers → ClickHouse/архив. ACK приложению соответствует устойчивой записи; broker bridge не удаляет сообщение до downstream ACK. Конфигурация Kafka — RF3, `min.insync.replicas=2`, `acks=all`, idempotent producer, unclean election отключён. При потере кворума не подтверждаем новые события. Размещение реплик по трём независимым доменам отказа и ресурсные квоты проверяются платформой.

Ключ партиции — `device_id`, не timestamp. Стартовая гипотеза — 12 партиций с проверкой skew/throughput; число не является результатом бенчмарка. Событие: `event_id`, `device_id`, `boot_id`, монотонный `sequence`, `captured_at`, `received_at`, координаты, качество GNSS и версия схемы. Для агрегатов используем event-time и watermark; поздние события пересчитывают проекцию. Consumer group — отдельная для карты/Delivery, архива и аналитики; дедупликация до расчёта метрик.

Предлагаем retention Kafka 72 ч, raw ClickHouse 30 дней, далее агрегации/архив только по утверждённому сроку и основанию обработки. Это не обещание хранить GPS бессрочно. Replay из архива учитывает dedup и tombstone/политику удаления. Устройство буферизует минимум 24 ч неподтверждённых событий как проектный target: объём = его частота × размер × 86400 плюс запас. Число устройств и частота на устройство неизвестны, поэтому конечный размер памяти не задан. Тревоги по заполнению буфера и разрывам sequence нужны до потери данных.

При 1 KiB и постоянном пике — 259.2 млн событий/сутки, 265.42 GB/сутки; RF3 ×72 ч = 2.39 TB payload. При лимите заполнения 70% — ≥3.41 TB дисков Kafka без служебного overhead. Raw 30 дней — 7.96 TB до репликации/индексов; это отдельная статья хранения. CPU, IOPS, сеть и пики восстановления определяются нагрузочным тестом. На перегрузке ограничиваем отдельные устройства, сохраняем durable backlog; запрет терять подтверждённые данные не отменяет конечность буферов.

## 7. Размещение, HA и восстановление

Базовый вариант — действующая платформа холдинга в российских ЦОД при достаточной мощности; managed-сервисы допустимы после ИБ/юристов и TCO. Не строим собственный Kubernetes ради задания, используем имеющуюся платформу/VM, если она обеспечивает нужную изоляцию и HA. Gateway и сервисы имеют минимум две реплики по доменам отказа, разделённые thread/connection pools; БД и брокеры требуют отдельного quorum/fencing решения. Отказ одного узла не должен оставлять систему без мощности на 200+3000 RPS.

| Контур | Проектная цель RPO / RTO | Механизм и предел |
|---|---|---|
| Orders/Warehouse/Finance/Payments | RPO 0 для подтверждённых операций при отказе одного узла; RTO ≤5 мин | Синхронная репликация PG, fencing, проверенный failover; кворум недоступен — запись не подтверждается |
| Profile | RPO 0 / RTO ≤5 мин при отказе узла | Отдельный HA-кластер, шифрование, отдельные ключи и backup; недоступность не обходится копией ПДн в Orders |
| Telemetry | RPO 0 для ACK в модели отказа одного узла; ingest RTO ≤1 мин | Репликация и durable bridge, device buffer для unacked; ≤72 ч backlog до исчерпания Kafka retention |
| CRM/аналитические проекции | RPO 0 по доступному журналу; rebuild RTO ≤4 ч | Replay от checkpoint/снимка, свежесть показывается клиенту; задержка >5 с всё равно нарушает DWH SLA |
| Потеря площадки / разрушение данных | Предложение: RPO ≤5 мин, RTO ≤60 мин | Изолированные backup+WAL/PITR и DR; **не соответствует автоматически** годовому SLA и RPO 0, требует утверждения/дополнительного бюджета |

Резервные копии: daily full/incremental по платформенному стандарту + непрерывный архив WAL, шифрование, неизменяемая копия в отдельном failure/security domain, месячный restore и квартальное DR-учение. Предложенный PITR retention — 35 дней, долговременные финансовые копии — по юридическому сроку. Для PII предусматривается удаление по политике при восстановлении старой копии. Пароли/ключи не помещаются в образы, конфигурация внешняя, процессы stateless, логи stdout без PII; локальная память не является единственным хранилищем принятой работы.

99.95% означает 262.8 минуты простоя за 365 дней. RTO — цель одного восстановления, а не весь бюджет: несколько инцидентов могут исчерпать его. Месячный operational budget для 30 дней — 21.6 минуты. RTO 60 минут при потере площадки превышает месячный эквивалент; нельзя обещать одинаковую доступность при любой катастрофе. Область SLA и резерв мощности утверждаются со спонсором.

| Область | Предпочтение | Альтернатива / условие выбора |
|---|---|---|
| OLTP | PostgreSQL, знакомый исходной команде | Коммерческая поддержка/managed PostgreSQL при нужном RTO; смена DBMS не решает междоменные JOIN сама по себе |
| Потоки | Kafka, CDC через Debezium/pgoutput после PoC | Платформа streaming холдинга, если обеспечивает replay/порядок/retention; коммерческий CDC при доказанной работе со standby и меньшем TCO |
| IoT storage | ClickHouse, time-series partition по дате | Существующее TSDB холдинга после того же capacity-теста; оценить стоимость индексов, late events и удаления |
| Gateway/BFF | Envoy или действующий корпоративный gateway; BFF по каналам | Коммерческий API manager при обязательных функциях управления; бизнес-Saga остаётся в домене |
| Наблюдаемость | OpenTelemetry, Prometheus/Grafana и корпоративный лог-контур | Платформа холдинга предпочтительнее дублирования; не логировать payload ПДн/карт |

OSS сокращает лицензионные платежи и зависимость от вендора, но требует on-call, обновлений, интеграции и экспертизы. TCO включает труд, инфраструктуру, лицензии/поддержку, DR, безопасность и двойную эксплуатацию. Выбор окончательный только после сопоставления с каталогом платформ холдинга; нельзя оправдывать стек одним словом «бесплатно».

TOGAF используется как структура управления: Business — отгрузки/EDI и владельцы процессов; Data — мастерство и классификация; Application — контексты/API; Technology — размещение/HA. Baseline и gaps отражены в Task1, Target — в C4, пакеты работ имеют владельцев. Штаб ведёт архитектурный repository, рассматривает исключения и проверяет соответствие после каждого этапа. Новые доменные сервисы публикуют outbox-события вместо табличного CDC; миграция DWH имеет overlap-сверку и один авторитетный источник для когорты. После отключения последнего домена legacy CDC и монолит выводятся из эксплуатации.
