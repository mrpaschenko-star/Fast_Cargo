# Панель KPI эксплуатации целевой архитектуры

Значения с пометкой **кейс** обязательны по заданию; **предложение** требует утверждения владельцем. Проектные цели не являются результатами измерений. M1–M12 отсчитываются от утверждения проекта; доступность за год проверяется по полному эксплуатационному окну, а не по дате завершения миграции.

| Технический показатель (KPI) | Целевое значение метрики | Способ и инструмент замера / формула | Бизнес-смысл |
|---|---|---|---|
| Доступность транзакционного ядра | **Кейс:** ≥99.95%, 24×7 за год | Prometheus/Grafana + внешние probes создания/чтения заказа и переходов исполнения. Временной SLI: `1 − unavailable_seconds / calendar_seconds`; согласовать семантику unavailable по критическим сценариям и регионам, все плановые простои учитываются | Сохранение приёма заказов и исполнения отгрузок |
| Успешность запросов ядра | **Предложение:** ≥99.95% за скользящие 30 дней, отдельно по операции/партнёру | `good_eligible_attempts / eligible_attempts`; good — устойчиво принятая команда или корректный бизнес-отказ. Считаем попытки после аутентификации и валидации; timeout, capacity 429, 5xx, неверный 2xx — bad. OpenTelemetry + gateway и доменные метрики | Не маскировать частичный отказ усреднением или формальным HTTP 200 |
| Скорость доставки ключевых статусов | **Кейс:** commit→query-visible DWH ≤5 с к M3; максимум, не только P95/P99 | CDC commit time/LSN → время первой видимости версии в запросе DWH. Сквозной audit ledger, DWH probe и histogram; число `latency >5s`, pending age и gaps. Предложение: clock skew <100 мс, контроль NTP | У холдинга актуальные данные об отгрузках |
| Полнота аналитики и безопасность выгрузки | **Кейс:** все согласованные ключевые статусы, только обезличенные данные | Сверка ID/версий внутри защищённого контура по реплике/журналу, tombstone и txn boundaries; число suppressed/unexported и их возраст отдельно. В DWH не передаём внутренний связующий ledger | Быстрый поток без полноты не даёт прозрачности; подавление не скрывает нарушение SLA |
| Суточный масштаб | **Кейс:** до 500 000 отправлений/сутки | Unique `shipment_id` с завершённым согласованным lifecycle за 24 ч; replay-профиль этапов/документов и сверка доменных ledger. Тест не требует реального перемещения грузов; отдельно бизнес измеряет физическую пропускную способность | Возможность обслуживать объём сделки, а не только создавать пустые заявки |
| Пиковый приём заказов | **Кейс:** 200 RPS; **предложение:** P95 ≤500 мс, P99 ≤1 с на durable acceptance | k6/Gatling, профиль позиций/ключей и доля операций из production-like выборки; 60 минут 200 RPS одновременно с 3000 IoT RPS. 202 допускается только после устойчивой записи; completion lag измеряется отдельно | Не замедлять продажи при росте потока |
| Приём телематики | **Кейс:** 3000 событий/с, независимо от Warehouse/Finance | Producer/consumer IDs и счётчики durable ACK, sequence gaps, Kafka lag, end-to-end age; 60 минут отключения Warehouse/Finance при полной нагрузке. Предложение: ingest P99 ≤1 с | Работа телематики и оформления заказов при сбое отдельных доменов |
| Сохранность IoT | **Кейс:** отсутствие потерь при указанных отказах; **предложение:** RPO 0 для ACK при отказе одного узла, буфер устройства ≥24 ч | `acked_unique_ids − recovered_unique_ids = 0` после drain/replay. Не подтверждённые события и пробелы device sequence считаются отдельно. Chaos-тест брокера/consumer/сети, сверка archive | Ни брокерный ACK, ни MQTT QoS не подменяют фактическую сохранность |
| Исходы платежей | **Кейс:** 0% безвозвратно потерянных исходов из-за timeout | Сверка уникальных provider operations с ledger Payments, включая callback/polling/reconciliation. `unresolved_mature_operations / all_mature_provider_operations`; обязательно total pending + max age. Предложение: alarm >15 мин, инцидент >24 ч; 24 ч не объявляет pending «успешным» | Исключить незамеченные списания и ручной поиск потерянных оплат |
| Идемпотентность и обеспечение оплаты | **Кейс:** 0 оплат без законного stock/fulfilment основания; **предложение:** 0 повторных списаний/проводок | Audit join в выделенной контрольной проекции, не cross-domain OLTP JOIN: provider_ref ↔ intent ↔ invoice ↔ permit/fulfilment. Уникальные бизнес-ключи, тесты late callback/cancel race/duplicate | Не оплачивать необеспеченные счета и не списывать дважды |
| Скорость EDI | **Кейс:** real-time, жёсткий SLA; число в кейсе не задано. **Предложение:** P99 внутренней обработки каждого готового перехода ≤2 с | `durable next-document/outbox time − predecessor-ready time`; отдельно отправка/receipt партнёра, retry backlog и возраст pending. Численный end-to-end SLA подписывают владелец EDI и сети | Ускорить документы без выдуманного срока физической перевозки |
| ПДн, PAN и границы доступа | **Кейс:** физическая изоляция ПДн; 0 прямых внешних DB-подключений; PAN не поступает в Fast Cargo | Network policy tests, IAM-аудит, synthetic canary в Profile, тест провайдерского callback, DLP/лог-скан; инвентаризация копий/backup. «0 найденных» не равно доказательству юридического соответствия | Снизить риск утечки и расширения платёжного compliance scope |
| Актуальность CRM | **Предложение:** P99 истории ≤5 с, P95 API ≤300 мс | Event commit→History projection visible, API tracing; ответы содержат `as_of`/версию. Отдельный SLI доступа к Profile | Оператор видит историю с понятной свежестью, не перегружая OLTP |
| Восстановление | **Предложение:** transactional RPO 0/RTO ≤5 мин при отказе узла; DR RPO ≤5 мин/RTO ≤60 мин | Failover/restore drills, last acknowledged ID/LSN → восстановленный ID/LSN; таймер до успешной бизнес-пробы. Ежемесячный restore, ежеквартальный DR | Понимание реального окна потери/недоступности; restore не равен запуску процесса |
| Завершение демонтажа | **Кейс:** M12; **предложение:** 30 суток нулевого трафика перед выключением runtime | 0 маршрутов/запросов к легаси, 0 междоменных DB-прав; сверка активных сущностей и архивов, приёмка владельцев | Исключить «микросервисы» поверх прежней общей БД |
| Скорость безопасных релизов | **Предложение:** ≥1 независимый релиз/неделю на активный домен, change failure rate <10% | CI/CD deployment log + incident linkage, окно 90 дней; только реальные изменения, не пустые deployment | Сокращение текущего цикла >2 недель без роста аварийности |

## Определения и защита от неверных выводов

**Граница ядра.** Приём и чтение заказа, подтверждение складской операции и продвижение исполнения измеряются отдельными SLI. Приём `pending` во время отказа склада допустим, но не объявляет Warehouse доступным. Доступность банка и офлайн-устройства измеряются отдельно; причинность фиксируется, а пользовательский неуспех не исчезает из отчёта. Core availability нельзя вычислять только по ответам gateway 2xx/3xx: redirect не означает оплату, а 202 — завершённую доставку.

**Бюджет простоя.** За 365 дней: `365 ×24 ×60 ×(1−0.9995) = 262.8 мин = 4 ч 22 мин 48 с`. За 30 дней — 21.6 мин как operational ориентир; это не дополнительное обещание месячного SLA из кейса. Бюджет относится ко всем инцидентам вместе. Годовой временной SLI и доля успешных запросов — разные показатели и не взаимозаменяемы.

**DWH.** Время источника — commit, не начало долгой транзакции или `event.created_at`. Если штатный connector не раскрывает нужный commit timestamp, data-команда добавляет его в адаптере из replication protocol либо внедряет эквивалентный проверенный измеритель на реплике; source-код не меняется. Реестр соответствия остаётся внутри защищённой зоны. Для анонимного агрегата учитывается время всех вошедших изменений. Непереданные/подавленные данные не становятся «неподходящими» задним числом: конфликт с ≤5 с отражается отдельно и требует решения штаба. P99 служит диагностике, максимальное требование он не заменяет.

**Нагрузка.** 200 RPS ×86400 = 17.28 млн созданий/сутки при непрерывном пике; 500 тыс./сутки — другой профиль. Поэтому есть отдельный 24-часовой тест суточной цепочки и тест пика. Тесты фиксируют размер заказа, число позиций, стоимость валидации, повторов, EDI и долю чтений, чтобы не доказывать масштаб на пустом payload.

**Платежи.** Зрелая операция — операция, по которой получен окончательный ответ банка либо истёк согласованный reconciliation deadline. Нерешённые после deadline считаются нарушением, не удаляются из знаменателя; кейс не даёт deadline, 24 ч — предложение. Пока deadline не наступил, мониторим абсолютное число/возраст pending. Финальный target 0 не означает отсутствие сетевых timeout. В тестах перебираются потеря запроса, ответа, callback и повторная доставка.

## Владение и реакция

| Группа KPI | Владелец | Реакция |
|---|---|---|
| Доступность, заказ, восстановление | Platform/on-call + доменные owners | Page по недоступности; burn-rate по бюджету, остановка rollout при быстром расходе |
| DWH, CDC и полнота | Data team + владелец DWH | Alarm уже при lag >3 с; нарушение >5 с регистрируется, gap ведёт к остановке переключения |
| IoT | Telemetry team + инфраструктура | Квоты устройства, масштабирование consumers, alarm до заполнения диска/буфера |
| Деньги/EDI | Payments/Finance/EDI owners | Pending reconciliation, защита резерва; ручное разрешение исключений с аудитом |
| ПДн/PAN | ИБ + Profile/Payments owners | Закрыть нарушающий экспорт/доступ, incident process, оценка затронутых данных |
| ROI и срок M12 | Финансовый директор + спонсор | Пересмотр этапа/бюджета при отрицательном эффекте или нехватке ресурсов |
