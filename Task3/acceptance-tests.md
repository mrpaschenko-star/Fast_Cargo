# Сценарии приёмки и необходимые доказательства

Это программа будущих испытаний, **не отчёт о проведённых нагрузочных тестах**. В учебной работе проверены только документы, расчёты и изображения.

| ID / этап | Сценарий | Ожидаемый результат и доказательство |
|---|---|---|
| A01 / M1 | На копии проверить версию PG, read-only snapshot, слот standby, DDL и длительные транзакции | Зафиксированы версии и настройки, bootstrap+replay сходятся без primary SELECT; список несовместимостей закрыт до GO |
| A02 / M2 | Снимок на standby одновременно с insert/update/delete; crash connector до/после checkpoint | Нет потерянных состояний и дублей бизнес-фактов; сохранена txn consistency, сверка count/hash и версий в приватной зоне |
| A03 / M3 | 7 суток shadow CDC; DWH query probe для каждого согласованного ключевого статуса | Max commit→visibility ≤5 с; 0 gaps; отдельный отчёт всех suppressed/unexported. Если privacy задерживает выпуск, исходное требование не принято |
| A04 / M3 | Проверить артефакт легаси, ACL и SQL audit существующими средствами | 0 правок исходников, 0 новых SELECT к primary (включая introspection/heartbeat); replica-only hostname, нет fallback |
| A05 / M3 | Остановить sink/connector; довести lag до предупреждения без исчерпания диска | Alarm, stale marker, runbook ограничения WAL; заказ не деградирует >предложенных 5% P95. В тесте снятого slot gap обнаружен, resnapshot только с реплики |
| A06 / M6 | Потерять ответ банка после успешного списания, повторить callback/команду; подделать подпись | Одно списание/проводка, результат восстановлен по тому же intent; invalid подпись отклонена, durable ACK после inbox |
| A07 / M9 | Warehouse разрешает платёж; сеть рвётся; TTL резерва истёк; приходит поздний успех | Товар не возвращён в свободный остаток, счёт не отменён до подтверждения terminal cancel; нет оплаты необеспеченного заказа |
| A08 / M9 | EDI duplicate, DESADV перед ORDERS, частичная отгрузка, ошибка версии/суммы INVOIC | Документы дедуплицированы или ждут предшественника; неверный счёт блокирован; платежи только на разрешённые позиции/суммы |
| A09 / M9 | 60 минут: 200 RPS заказов +3000 IoT RPS; Warehouse и Finance остановлены | Приём pending-заказов сохраняет предложенные P95/P99; 0 потерянных ACK IoT, telemetry backlog drains после восстановления; завершение заказов не выдается за успешное во время остановки |
| A10 / M9 | Один брокер/consumer падает; устройство offline 24 ч, затем повторяет последовательность | 0 потерь подтверждённых событий; неподтверждённые восстановлены в пределах буфера; dedup, out-of-order, boot_id и gaps проверены |
| A11 / M12 | 24 ч: 500 тыс. lifecycle отправлений с репрезентативными позициями/EDI/оплатами | Все состояния и документы сверены, backlog не растёт бесконечно; физическая пропускная способность склада проверяется бизнесом отдельно |
| A12 / M12 | PG failover и restore из backup/WAL; отдельно потеря площадки | Выполнены согласованные RPO/RTO с проверкой acknowledged IDs; нет split-brain и повторного writer; затраты простоя внесены в бюджет SLA |
| A13 / M6–M12 | CRM запрашивает чужой профиль; поиск canary ПДн/PAN во всех исходящих потоках | Запрет неразрешённого доступа, физическая изоляция подтверждена; external DWH прошёл re-identification review; валидный профиль доступен законной роли |
| A14 / M12 | Переключение когорты до/после первой новой записи; поздние команды/повторы | Один writer/epoch, маршруты fenced; обратный перенос проверен либо используется forward-fix; нет слепого rollback на устаревшую БД |
| A15 / M12 | 30 суток наблюдения после финальной миграции | 0 legacy вызовов и чужих DB-доступов, все активные сущности сверены, runtime отключён, архив и legal retention приняты |

## Порядок переключения каждого домена

1. Владелец фиксирует модель, scope когорты, версии API/событий, сверку и допустимый rollback. После M3 переносит snapshot и delta; операции старого writer продолжаются до согласованного барьера.
2. Вводятся fencing/ownership epoch и короткий контролируемый drain команд когорты. Поздние команды сохраняются с прежним idempotency key; gateway направляет их актуальному владельцу. Одновременно писать в обе БД нельзя.
3. После сверки включается новый writer и небольшой canary трафик; доли 1% →10% →50% →100% — предложение с отдельным окном наблюдения и согласованием операций. Рост не автоматический при нарушенных KPI.
4. До новых записей доступен возврат маршрута. После новых записей — обратная синхронизация с проверкой полноты/фенсингом или исправление вперёд. Старый сервис не получает право записи, пока не стал актуальным владельцем.

## Свидетельства и подписанты

К каждому сценарию прикладываются версия окружения, профиль/seed данных, временной диапазон, dashboard/traces, запросы сверки на разрешённых хранилищах и результат pass/fail. Секреты и реальные ПДн в отчёт не включаются. Подписывают доменный владелец и QA; A01–A05 также DBA/data, A06–A08 финансы/EDI, A09–A12 инфраструктура, A13 ИБ/юристы. Финальный GO даёт операционный директор после архитектурного штаба.
